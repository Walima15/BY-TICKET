# Decisions & Assumptions

A running log of architectural decisions (lightweight ADRs). Newest phase at the bottom.
Each entry: **Decision** — why — consequences / how to revisit.

---

## Phase 1 — Scaffold

### D-001 Repository layout: light monorepo, no workspace tooling
**Decision:** `apps/web` (Next.js), `contracts/` (Cargo workspace), `supabase/` (SQL migrations + seed), `scripts/` (Node helpers), `docs/`.
The root `package.json` only holds convenience scripts that delegate with `npm --prefix apps/web`.
**Why:** Only one JS package exists today. npm/pnpm workspaces add hoisting complexity for no gain, and
installing inside OneDrive-synced folders is already slow. **Revisit** when a second JS package appears
(e.g. a shared `packages/contracts-client` generated by `stellar contract bindings typescript`).

### D-002 Next.js 16 (App Router) + React 19 + Tailwind v4 + shadcn/ui (Base UI preset)
Latest stable versions at time of writing. Notable Next 16 conventions we follow:
`proxy.ts` replaces `middleware.ts`; `app/manifest.ts` for the PWA manifest; Turbopack by default.

### D-003 One env file: `apps/web/.env.local`
**Decision:** the single env file lives where Next.js natively loads it, `apps/web/.env.local`
(template: `apps/web/.env.example`). `scripts/gen-secrets.mjs` and the contract deploy script write into it.
**Why:** contract IDs produced by the deploy script must reach the web app without copy/paste.
**Rejected:** a repo-root `.env.local` loaded via `@next/env` in `next.config.ts` — tried and verified broken:
`loadEnvConfig` caches Next's own first load and returns early, so root values never reached the build or
runtime (and dev env-reloads would drop them anyway).
Env is validated with zod (`src/lib/env.ts` public, `src/lib/env.server.ts` secrets); secrets never use `NEXT_PUBLIC_`.

### D-004 Testnet first, network is configuration
All Stellar endpoints / passphrase / contract IDs come from env (`NEXT_PUBLIC_STELLAR_NETWORK=testnet`).
Mainnet is a config + key-management change, not a code change (see ROADMAP).

### D-005 Soroban SDK 28, `wasm32v1-none` target
`soroban-sdk = 28.0.0` (MSRV 1.91). Contracts build for `wasm32v1-none`, the target `stellar contract build`
uses for current protocol versions. Release profile is size-optimised with `overflow-checks = true`
(arithmetic overflow must trap, never wrap, in money/capacity code).

### D-006 Three contracts, not one
`event_ticket` (events, tickets, transfers, check-in, revenue split), `rewards` (BY Points token),
`attendance_badge` (POAP). **Why:** independent upgrade paths and smaller WASM; `event_ticket` calls the
other two through cross-contract calls after purchase / check-in and is their only authorised minter
(plus admin).

### D-007 BY Points = custom SEP-41 token contract (not a classic asset wrapped by the SAC)
**Why:** a classic Stellar asset needs a trustline (and 0.5 XLM reserve) per holder — painful for
custodial/email users and for "points" that are meant to be free. A Soroban token implementing the SEP-41
interface works with contract-held balances, no trustline, and lets us add rules (minter allow-list,
optional non-transferability, perk redemption) that a plain SAC admin can't express.
**Trade-off:** points don't show in classic-only wallets. **Alternative kept open:** issue `BYPTS` as a classic
asset and make the `rewards` contract the SAC admin, if exchange-listing / wallet visibility matters later.

### D-008 Custodial fallback for non-crypto users
Email-login users get a server-generated Stellar keypair. The secret is encrypted with AES-256-GCM using
`CUSTODIAL_KEY_ENCRYPTION_KEY` (envelope encryption; swap the key provider for a KMS in production) and stored
encrypted in Supabase; plaintext only exists in memory while signing. Accounts are created/sponsored by the
platform account so users never need XLM. Users can "graduate" to self-custody by linking Freighter.

### D-009 Signed, rotating QR with offline verification (design; implemented in Phase 5)
- Server issues a short-lived **ticket credential**, Ed25519-signed with `QR_CREDENTIAL_SIGNING_KEY`, binding
  `ticket_id`, current owner, and the holder device's public key (non-extractable WebCrypto key).
- The holder's device renders a QR every ~20 s: `credential + timestamp`, signed by the device key.
- Scanners verify **offline** with only the public key `NEXT_PUBLIC_QR_CREDENTIAL_PUBLIC_KEY`, reject stale
  timestamps (screenshots expire), and de-duplicate check-ins locally; queued check-ins sync to the chain via
  `validate_and_check_in` when back online. The contract is the final arbiter of double entry.

### D-010 Payments: USDC/XLM on Stellar, ZMW shown for display, mobile money behind an adapter
Prices are stored in USDC (7-decimal stroop-style integers on-chain). ZMW is a display conversion from an FX
rate (`NEXT_PUBLIC_ZMW_PER_USDC` fallback; pluggable provider later). Mobile money (MTN MoMo, Airtel Money,
Zamtel Kwacha) is behind a `PaymentRampAdapter` interface with a stub implementation only.

### D-011 Rate limiting: Upstash Redis when configured, in-memory fallback
Serverless-friendly; dev works with zero setup. In-memory limits are per-instance, so production must
set `UPSTASH_REDIS_REST_URL`/`_TOKEN`.

### D-012 Supabase new-style API keys
Uses `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_…`) and `SUPABASE_SECRET_KEY` (`sb_secret_…`).
Legacy `anon` / `service_role` JWT keys work in the same variables.

### D-014 Contract build environment on this Windows machine (open)
Found during Phase 1 verification:
- The default `stable-x86_64-pc-windows-msvc` toolchain has no linker: Visual Studio 2022 Community is
  installed without the C++ workload / Windows SDK.
- Workaround installed: `stable-x86_64-pc-windows-gnu` (bundled linker). `cargo build` of the contracts succeeds.
- `cargo test` is blocked by Windows **Application Control (os error 4551)**, most likely Smart App Control:
  it refuses to execute the unsigned build-script binaries Cargo compiles for the `testutils` feature set.
Options: build/test inside a Docker Linux container (Docker Desktop is installed), WSL2, CI (GitHub Actions),
or turning Smart App Control off. To be decided before Phase 2.

### D-013 Development inside OneDrive
The workspace lives in a OneDrive-synced folder. That works but makes `npm install` / `cargo build` slow and
can cause file-lock errors. Recommended: move the repo outside OneDrive, or mark `node_modules`, `.next`, and
`contracts/target` as "always keep on this device" / excluded from sync.
